# リリースPR本文の作成

指定されたベースブランチと反映元ブランチの差分を確認し、過去の同種PRに合わせて日本語の本文を作成する。指定がなければ `dev` → `master` を対象とする。

## 調査

- リモートURLから対象リポジトリを確認する。本プロジェクトの開発リポジトリは `revati-jp/studio-website-dev`。
- 過去の同種PRを読み、見出し・粒度・コミット参照の形式を合わせる。
- 開発リポジトリのPRを取得できない場合、公開ミラー `revati-jp/studio-website` の過去PRを参考にできる。PR番号は両リポジトリで共通とは限らない。
- ベースに未反映のコミット一覧と差分を確認する。例えば `git log origin/master..origin/dev` と `git diff origin/master...origin/dev` を使い、コミットメッセージだけでなく実際の変更内容を読む。現在の作業ブランチの変更を混ぜない。
- 最新のリモート情報を取得できない場合は、ローカルの参照で作成し、その制約を本文の外で短く伝える。

## 本文の好み

- WORKの追加は「## WORKの追加」にまとめる。
- WORK追加のコミットには必ずIDを付け、その下に「クライアント名: 作品名」を列挙する。件数を書く場合は実際の追加件数に合わせる。
- コミット参照は `[完全なコミットSHA]` の形式にする。
- 独立した機能追加や改善は、必要に応じて見出しを設ける。
- 整形・依存関係更新・軽微な整理は「## その他」にまとめ、コミットを一つずつ列挙しない。AstroやNode.jsのメジャー更新など、重要な更新はまとめた項目内で明記する。
- WORK以外のコミットIDは、独立した機能追加・改善・手順追加など、変更の追跡に役立つものだけ付ける。
- 実施していないテストや確認結果は記載しない。
- 調査の経緯や会話の履歴はPR本文に含めない。

## 出力

コピーできるMarkdownコードブロックで本文を提示する。本文作成の依頼だけでは、GitHubへのPR作成・更新は行わない。
